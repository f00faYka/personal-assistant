# Offline draft synchronization

`POST /offline-drafts/sync` accepts a client-owned `draftId` together with a Member identity and the original audio or text. The `(memberId, draftId)` pair is the idempotency identity. Retrying the same original returns the same durable draft; retrying it with different source content returns `409`.

An `accepted` draft means that the server has durably retained the original and, for audio, linked it to one Capture. It does not mean that transcription, interpretation, or a Task/Note has been confirmed. A failed audio handoff remains durable with `retryable: true`, and a later retry can complete the handoff. Downstream processing and its confirmed-result state remain separate from this synchronization boundary.

`GET /offline-drafts/<draft-id>/status?memberId=<member-id>` exposes the read-only synchronization contract. `state` is `accepted` for a durable text draft, `processing` after an audio Capture handoff while downstream work is pending or failed, `confirmed` when the linked review has a durable Task or Note, and `failed` when synchronization failed. `processing` separately reports `not_started`, `pending`, `failed`, or `confirmed`; `capture` and `result` links remain distinct. Failed states include a retryable or terminal classification and a client-safe message. Invalid submissions return HTTP 400 with the same terminal-failure shape; they are not persisted as drafts. Repeated reads return the same identifiers and state until a later synchronization or downstream result changes it.
